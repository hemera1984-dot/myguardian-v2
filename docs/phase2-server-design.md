# 2차 공사 설계서 — 팀 공유 백엔드 (착공판, 2026-07-26 재작성)

2026-07-19 초안을 폐기하고 확정 결정 기준으로 다시 썼다. 반영한 결정:
Cloudflare 폐기·NCP 단일화(07-20), 역할·권한 모델 3.0(07-20), 구글 OAuth + 관리자 승인(07-20).

착공 순서는 STEP 0(사용자 콘솔 준비) → STEP 1(인증·승인) → STEP 2(고객 데이터) 순이다.

## 이 공사가 푸는 문제

1차(순수 정적 + 로컬 폴더)는 혼자 쓸 때는 완결이지만 팀으로 넓히면 막힌다.

| 막히는 곳 | 1차의 한계 |
|---|---|
| 로그인 | 없다. intro.html의 구글 버튼은 브라우저 표시만 남기는 껍데기다 |
| 화면 차단 | 정적 사이트라 브라우저에서 막아도 소스를 열면 보인다. 실효가 없다 |
| 팀원 고객 데이터 | 각자 PC 로컬 폴더 + git. 동기화를 누르지 않으면 갈라진다 |
| 팀 공지·일정 | 정적 JSON이라 화면에서 쓸 수 없다 |

## 핵심 원칙 — 차단은 서버가 한다

브라우저에서 화면을 숨기는 것은 차단이 아니다. **승인되지 않은 계정에는 서버가 데이터를
주지 않는 것**이 차단이다. 따라서 인증(STEP 1)과 데이터 이전(STEP 2)은 한 묶음으로 간다.

- 화면 게이트(로그인 안 하면 intro로 보냄)는 사용자 경험용이며 보안 수단이 아니다.
- 공개 데이터(사례·판례 383건, 사전, 케어 발행물)는 지금처럼 공개로 둔다. 감출 이유가 없고
  GitHub Pages가 더 빠르다.
- 보호 대상은 고객 개인정보와 팀 내부 데이터뿐이다.

## 무엇을 서버로 옮기고, 무엇을 남기나

**서버(NCP)로**
- 계정·승인·직급 (STEP 1)
- 고객 데이터 — 프로필·메모·보유보험. FC별 소유권 (STEP 2)
- 팀 공지·일정·출근 현황 (STEP 3)
- 케어 발행 중계 — API 키를 서버에 두고 브라우저에 노출하지 않는다 (STEP 4)

**로컬에 남김**
- 보장분석 파일·상담 영상 — 본인 기기 전용
- 브리핑 자료 라이브러리(IndexedDB) — 발표 자료는 기기 안에 둔다
- 공개 데이터 — 사례·판례·사전·케어 발행물 본문

화면·스키마는 그대로 두고 **저장 경로만 추가**한다. 1차 스키마가 그대로 서버 테이블 규격이 된다.

## 인증·인가 설계

### 인증 — 구글 OAuth

- 자체 회원가입·비밀번호 저장 금지 (헌법). 구글 계정으로만 로그인한다.
- 흐름: 브라우저에서 구글 로그인 → 구글이 발급한 ID 토큰을 서버로 전달 →
  **서버가 구글 공개키로 토큰을 검증** → 서버가 자체 세션 토큰 발급.
- 토큰 검증은 반드시 서버에서 한다. 브라우저가 "로그인했다"고 주장하는 것은 신뢰하지 않는다.

### 인가 — 승인이 있어야 열린다

구글 로그인만으로는 아무것도 열리지 않는다. 계정 상태는 셋이다.

| 상태 | 의미 | 접근 |
|---|---|---|
| 대기 | 로그인은 했으나 승인 전 | 승인 대기 안내 화면만 |
| 승인 | 팀원으로 승인됨 (직급 부여) | 자기 데이터 |
| 정지 | 퇴사·회수 | 대기와 동일하게 차단 |

### 승인 권한 — 데이터로 켜고 끈다 (2026-07-26 개정)

기존 결정은 "승인은 총관리자 전용"이었으나, **팀장급도 자기 산하 팀원을 승인**할 수 있게
넓힌다. 단 직급명을 코드에 박지 않는다 — 직급 데이터에 권한 플래그를 둔다.

- `팀원승인` 플래그를 가진 직급은 **자기 하위 트리의 대기 계정만** 승인할 수 있다.
- 총관리자는 전 범위 승인·직급 변경·정지·관리자 임명이 가능하다.
- 관리자 임명·회수는 총관리자 전용 (기존 유지).
- 이 플래그는 `data/team/org.json`의 직급표에 실어 화면에서 바꿀 수 있게 한다.

열람 범위는 **B안 유지**: 고객은 각자 자기 것만 본다. 승인 권한이 있다고 해서 하위 팀원의
고객을 볼 수 있는 것이 아니다. 전체 고객 열람은 총관리자만.

## STEP 0 — 사용자 콘솔 준비 (선행, 대행 불가)

계정 생성·결제수단 등록·인증키 발급은 사용자가 직접 해야 한다. 아래를 끝내야 착공한다.

**구글 클라우드 콘솔**
1. 프로젝트 생성
2. OAuth 동의 화면 구성 (내부 또는 외부, 앱 이름 "마이가디언")
3. OAuth 클라이언트 ID 발급 — 웹 애플리케이션
4. 승인된 자바스크립트 원본에 `https://hemera1984-dot.github.io` 등록
5. 클라이언트 ID를 시공자에게 전달 (클라이언트 ID는 공개해도 되는 값이다)

**NCP 콘솔**
1. 결제수단 등록
2. 서버 생성 — Micro Server(결제수단 등록일부터 1년 무료, 한국 리전) 또는 Cloud Functions
3. DB 준비 — Cloud DB for MySQL 또는 서버 내 설치형
4. 계정 Access Key 발급 (검색 API 키는 서버·DB 자격이 아니다)
5. 도메인·HTTPS 인증서 (GitHub Pages에서 서버를 부르므로 HTTPS 필수, CORS 허용 필요)

**선행 조건 (2026-08-02 사용자 결정으로 개정)**
- 종전의 "회사 규정 확인 통과" 게이트는 폐기한다. 대신 **종단간 암호화**를 전제로 한다:
  서버에는 판독 불가능한 암호문만 올라가고 열쇠는 FC의 기기에만 존재한다. 서버 운영자도,
  클라우드 사업자도, 유출자도 내용을 읽을 수 없으므로 "고객정보를 외부 클라우드에 보관"이
  아니라 "암호문을 보관"이 된다. 마스킹 단독안보다 강하고, FC 화면에서는 원문을 그대로 쓴다.

## STEP 1 — 인증·승인 (착공 1순위)

**서버**
- `POST /auth/google` — 구글 ID 토큰 검증 → 세션 토큰 발급, 신규면 대기 계정 생성
- `GET /me` — 내 계정 상태·직급·권한
- `GET /admin/pending` — 승인 대기 목록 (승인 권한자만, 자기 범위만)
- `POST /admin/approve` — 승인 + 직급 부여
- `POST /admin/suspend` — 정지·회수
- 모든 보호 경로는 세션 토큰 검증 + 상태가 승인인지 확인

**화면**
- intro.html — 진짜 구글 로그인으로 교체, 전 화면의 진입점으로 연결
- 승인 대기 화면 — 로그인은 됐으나 미승인일 때
- admin — 승인 대기 목록·승인·직급 부여·정지 (현재 안내문만 있는 화면을 채운다)
- 공통 게이트 — platform.js에서 세션 확인, 없으면 intro로

## STEP 2 — 고객 데이터 (종단간 암호화 전제)

**암호화 설계 (2026-08-02 확정 — 전체 암호화)**

경위: 처음에 "보장분석이 서버에서 돌아야 하니 분석 필드는 평문" 이라는 봉투 분리안을 세웠으나,
보장분석 파이프라인은 Claude API 서버 호출이 아니라 **클로드코드·코덱스로 FC의 PC에서 도는
로컬 공정**임이 확인되어(2026-08-02 사용자 확인) 전제가 사라졌다. 서버가 내용을 읽을 이유가
없으므로 **레코드 전체를 암호화**한다 — 더 단순하고 더 강하다.

- 서버 스키마: `고객코드`·`소유 계정`·`갱신시각`·`암호문`. 그 외 아무것도 없다.
- 검색·정렬·필터·통계는 기기에서 한다. 목록을 받아 복호화 후 처리 —
  고객 수백 명 규모라 체감 차이가 없다.
- 서버 통계가 정말 필요해지는 날이 오면 그때 비식별 컬럼을 추가한다. 기존 암호문은
  그대로 두면 되므로 재암호화가 아니다. 미리 나눠 두지 않는다.

**열쇠 단위 — FC 개인 (2026-08-02 사용자 확정)**
- 고객은 담당 FC 한 명만 본다. 인수인계·이관·조인웍이어도 마찬가지다. 지점 공용 열쇠를
  두지 않는다.
- 이관 절차: 원 FC가 서버 레코드를 내려 복호화 → 현행 이관 기능으로 폴더 이동 →
  새 FC가 자기 열쇠로 다시 올림. 서버에는 항상 한 사람의 열쇠로만 존재한다.
  공개키 교환·재암호화 프로토콜을 만들지 않는다.
- 총관리자도 내용을 읽지 못한다. 전체 열람은 "어느 FC가 몇 명을 관리 중인가" 메타데이터뿐.


- 알고리즘: 브라우저 표준 WebCrypto AES-GCM 256. 외부 라이브러리 없음(헌법: 의존성 0).
- 열쇠: FC가 정한 잠금문구에서 PBKDF2로 파생. 서버는 잠금문구도, 파생 열쇠도 받지 않는다.
- 기기 추가: 잠금문구를 새 기기에서 한 번 입력하면 같은 열쇠가 복원된다(서버 왕복 없음).
- 분실 대비: 잠금문구를 잊으면 복구 불가 — 이 사실을 설정 화면에 명시하고,
  로컬 폴더 내보내기(현행 기능)를 백업 경로로 유지한다.
- 검색: 서버는 암호문을 검색할 수 없다. 목록을 받아 기기에서 복호화 후 검색한다
  (고객 수백 명 규모라 성능 문제 없음).
- 일정 연동(ourbranch)은 지금처럼 마스킹 표기만 보낸다 — 팀 캘린더는 공유 화면이므로
  암호화 대상이 아니라 애초에 최소 정보만 나간다.

- FC별 소유권. 총관리자만 전체 열람 (B안) — 단 암호문이므로 총관리자도 내용은 못 읽는다.
  전체 열람은 "어느 FC가 몇 명을 관리 중인가" 수준의 메타데이터에 한정된다.
- 조인웍 공유 — 프로젝트에 속한 고객만 상호 공유. 폴더·전체 공유 아님
- 로컬 폴더 모드를 남겨 오프라인·통신 장애에 대비
- 내보내기(JSON) 유지 — 탈출 경로 확보

## STEP 3 — 팀 공지·일정 쓰기

우리팀 화면에서 팀원이 직접 등록. 직급 트리는 전달 범위 산정에 쓴다.

## STEP 4 — 케어 발행 중계·브리핑 기기 간 동기화

- 발행: 주제 선택 → 생성 → 초안 편집 → 발행. API 키는 서버에 둔다
- 브리핑: 1차의 메시지 규격(v1.1)을 그대로 쓰고 운반 계층만 BroadcastChannel → 서버로 교체.
  브리핑 엔진이 이미 운반·규약 계층으로 분리돼 있어 교체 지점이 한 곳이다

## 헌법 개정안 (착공 시 반영)

현행 "상시 서버·데이터베이스·로그인 기능 금지" 조문을 다음으로 바꾼다.

> - 화면과 공개 데이터는 순수 정적을 유지한다 (HTML·CSS·JS·정적 JSON).
> - 팀 공유가 필요한 기능(계정·승인, 고객 데이터, 팀 공지·일정, 발행, 브리핑 동기화)에 한해
>   NCP 서버와 관리형 데이터 저장소 사용을 허용한다.
> - 자체 회원가입·비밀번호 저장은 금지한다. 인증은 구글 계정(OAuth)으로만 한다.
> - 인가는 승인제다. 승인되지 않은 계정에는 서버가 데이터를 주지 않는다.
> - 서버는 저장·중계만 담당한다. 데이터 신뢰성 원칙은 서버에도 동일 적용한다.
> - 고객 개인정보는 공개 저장소·공개 경로에 두지 않는다.

## 착공 전 확인 사항

1. **개인정보 처리위탁** — 외부 클라우드 보관에 따른 위탁 고지·수탁자 관리 의무 확인.
   국내 리전이라 국외 이전 문제는 없다.
2. **회수 절차** — 팀원 퇴사 시 계정 정지 + 담당 고객 이관 절차를 정한다.
3. **백업** — DB 스냅샷 주기, 로컬 내보내기(JSON) 유지.
4. **오프라인 대비** — 상담 현장에서 통신이 끊겨도 고객 조회가 되도록 로컬 캐시 유지.
5. **비용** — 착공 시 요금 계산기로 산정 (https://www.ncloud.com/charge/calc/ko).
